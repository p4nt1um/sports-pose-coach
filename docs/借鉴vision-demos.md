> 分析对象：`E:\GithubPrj\vision-demos`（Apache-2.0，8 个健身/攀岩视觉演示）
> 分析日期：2026-10-28
> 结论面向：`sports-pose-coach`（实时浏览器端）与 `kids-motion-screening`（儿童体感观察）

## 零、一句话结论

**它和你是两条互补的路线，不是替代关系。** 它的价值不在"能跑什么动作"（大部分你已有），
而在于**它把每个动作的算法都写成了一份可验证的方法论**——尤其是「用本人的满程当基准」（自校准）
和「用置信度选近侧肢体」这两件事，是你现在缺的。

我已经在你的代码里查实了三处对应的隐患，见第三节。

## 一、两条路线对比：不可互换

| | vision-demos | sports-pose-coach |
|---|---|---|
| 形态 | Python 脚本 + Gradio，处理**离线视频** | 纯浏览器单页，**实时摄像头** |
| 姿态模型 | ViTPose+ Large（云 API，COCO-17） | MediaPipe BlazePose（本地，33 点） |
| 关键点精度 | 高（专门为姿态设计的大模型） | 中（轻量实时模型） |
| 延迟 | 一条视频几分钟 | 单帧 19ms |
| 成本 | 按调用计费（`run.json` 记录每次开销） | 零（本地推理） |
| 联网 | 必须（`VLMRUN_API_KEY`） | 不需要（完全离线） |
| 适用 | 课后精修、报告、研究 | 课堂实时反馈、一体机 |

**所以不能"把它的技术搬过来替代你现在这条"** —— 搬 ViTPose 就意味着要联网、要计费、失去实时，
直接破坏你「零依赖 / 完全离线 / 视频不出本机」这条对外承诺。

**正确的借法是借方法论，不是借架构。**

## 二、值得直接借的 8 个技术点（按 价值/成本 排序）

### ① 近侧/远侧按「整段置信度」选，不是按值选　成本：小　价值：高

**他们怎么做**（`push_ups/src/form.py`）：
侧拍时远侧手臂和腿被身体挡住，模型在猜。所以每个测量都用**近侧**，
而"哪侧是近侧"由**整段视频里肩/肘/腕/髋/膝/踝六个点的平均置信度**决定（示例片段：右侧 0.95 vs 0.84）。
`--side` 可以强制指定。

**你为什么需要**：俯卧撑、仰卧起坐、靠墙静蹲都是侧拍。你现在 `squat` 用 `side: "min"`，
`min` 是**按数值**取更弯的那条腿 —— 远侧腿被遮挡时模型会给出离谱角度，
`min` 会把这个坏值选中。

**改哪里**：`shared/tpc-signals.js` 的 `sideList()` / `reduce()` 增加一个
`side: "auto"`，语义是"取累计置信度更高的一侧"，结果在本次会话内锁定（不要每帧切换）。

---

### ② 身体直线用「髋偏离肩-踝连线的角度」　成本：小　价值：高

**他们怎么做**（`push_ups/how-it-works.md`）：
`body line = 髋相对于「肩→踝」直线的偏离角`。0° 是刚性平板，负=髋下沉，正=髋抬高，
全程 ±15° 内算直背。并且明确写了：**关键点不在关节中心，视觉上笔直的平板读出来是 −4°~−9°**，
所以阈值必须留这个偏差。

**你现在的做法**：`pushup.signals.bodyLine` 的类型是 `torsoLean` —— 那是**躯干与竖直方向**的夹角。
它能判断"身体是否够水平"，但**看不到髋部下沉**（髋下沉是躯干和腿之间的折角，不是躯干倾角）。

**改哪里**：`tpc-signals.js` 加一个 `type: "lineDeviation"`（三点：肩—髋—踝，算髋到直线的垂距/角度），
`pushup` 与将来的"平板支撑"都用它。公式几行就够。

---

### ③ 每次读数取「5 帧中位数的极值」　成本：小　价值：中

**他们怎么做**：`push_ups` 明确写 "Each reading is the extreme of a 5-frame median,
so one bad pose can't decide a rep."（每次读数取 5 帧中位数的极值，一帧坏姿态决定不了一次判定）

**你现在的做法**：单帧判定 + 一欧元滤波。滤波压不住"连续 2–3 帧的异常"。
半程闸门和迟滞带解决的是"抖动跨阈值"，不是"读数本身被一帧污染"。

**改哪里**：`tpc-fsm.js` 的相位进入条件里，把单帧值换成"最近 5 帧中位数"再判。

---

### ④ `legLength` 改成「中位大腿 + 中位小腿」　成本：小　价值：中

**他们怎么做**（`running/cadence-explained.md`）：
腿长不能用 `|髋_y − 踝_y|` 的平均 —— 跑步时膝盖一直是弯的，那个平均其实测的是"弯了多少"，
实测会**短 8–11%**。正确做法是把大腿和小腿**分别按线段长度**算，各取中位数再相加。

**你的问题**：`resolveScale` 里 `legLength = pick(23, 27)`，就是 髋→踝 的直线距离。
动作中膝盖一弯，这个距离就缩短 —— 正好是你自己在 `meta.holdFields` 里记过的
「归一化长度必须对被测动作不敏感」那类问题。

**但先别急着改**：目前只有 `squat.hipDrop` 用它，而 `hipDrop` 是**死配置**（见第三节）。

---

### ⑤ 相位切分用「最快速度的 10%」往回推　成本：小　价值：中

**他们怎么做**（`chin_ups` / `push_ups`）：
从向心段速度**最快的点**出发，往前往后各走，直到速度落到最快点的 10% 以下 ——
这样就得到"真正开始离开底部"和"锁定"的时刻，**底部停顿的时间不算进去**。
他们因此能同时给出向心（concentric）和离心（eccentric）时长。

**你为什么值得有**：体育教学里"下降 2 秒、上升 1 秒"是真实的教学语言（离心控制）。
你现在 `minRepMs/maxRepMs` 量的是整周期或半周期，给不出向心/离心拆解。

---

### ⑥ 计数与分级分离：**都算进次数，质量单独列**　成本：中　价值：高（但要产品决策）

**他们怎么做**：`pull_ups` 和 `push_ups` 都反复强调同一句：
"Every rep counts, short ones included. **Grading is a separate step.**"
面板上是「12 次 · 满程 10/12 · 直背 9/12」。

**你现在的做法**：不合格直接不计（"半蹲 30 次 → 一次都不算"）。

**这不是 bug，是两种产品哲学**：

| | 严格计数（你现在） | 宽松计数 + 分级（他们） |
|---|---|---|
| 适用 | 体育课达标、考试 | 课堂激励、儿童体感、长期趋势 |
| 学生的感受 | "我做了 30 个，屏幕说 0" | "我做了 30 个，其中 22 个标准" |
| 趋势分析 | 只看到"合格次数" | 能看到"合格率在上升" |

**建议**：体育课保持严格；`kids-motion-screening` 一定要用宽松计数 + 合格率 ——
儿童阶段最重要的是"愿意继续做"，不是"做对几个"。

---

### ⑦ 自校准 profile：用「这个人自己的满程」当基准　成本：中　价值：极高

**他们怎么做**（`pull_ups/src/calibrate.py`，这是整个项目最值得学的一段）：

- 直臂**不是 180°**：ViTPose 把肩点放在三角肌上，死悬读数约 **167.5°**，而且**因人、因机位而异**
- 所以让运动员先做一组满程动作，从中**学出三个值**：

| 学到什么 | 样例片段的值 | 阈值取法 |
|---|---|---|
| 直臂角 | 167.5° | 满程悬挂 ≥ 155° |
| 头部过杠高度 | 0.42 躯干长 | ≥ 0.17（即 40%） |
| 肘部扫角 | 132° | ≥ 46° 屈曲（即 35%） |

- 然后所有阈值都取**比例**（40%、35%），不是绝对值
- 没有 profile 时退化为"用片段自己的最深悬挂当基准，150° 兜底"——能跑，但"最深那次特别深"会连累其余每次

**你为什么需要**：你的阈值全是绝对值（膝角 78–132°、踝距 0.35–1.8 肩宽）。
对成年人有效，但**小学生和幼儿园孩子的关节比例、柔韧度差异极大**；
同一个 100° 膝角，对 6 岁和 12 岁是完全不同的动作幅度。

**改哪里**：
1. `tpc-store.js` 已有"按 id 存差异 patch"的能力 → 加一层 `profiles.<studentId>`
2. 加一个"校准流程"：做 3 次标准动作 → 取满程 → 学出该生的三个基准
3. `exercises.json` 的阈值支持 `{ "pctOf": "profile.fullRange", "ratio": 0.4 }` 这种写法

**这是儿童体感能不能成立的关键。** 没有它，你会不断收到"这个孩子明明做对了却不计数"的反馈。

---

### ⑧ 相似度指标的双锚点自校准　成本：中高　价值：极高（主要给儿童体感 / 教学对比）

**他们怎么做**（`dance_sync/similarity-metric-explained.md`，算法设计非常成熟）：

- 每个舞者建**自己的躯干坐标系**（原点髋中点，向上指向肩中点），在里面量 12 段身体段的**方向角**
  —— 用角度而非坐标，身高和肢长差异就不会被当成"不同步"
- **分段加权**：核心（躯干、大腿、颈）权重大于末端（手臂本来就因人而异）
- **±2 帧容忍**：一帧的偏差算到"节奏"头上，不算"形状"
- **0% 和 100% 两个锚点都从片段自己身上测**：
  - **0%** = 相隔 ≥2 秒的帧之间的中位差异（"两个无关瞬间本来就有多像"）
    → 因为两个直立人体本来就"意外地像"，不扣掉这个底，分数会报出并不存在的同步
  - **100%** = 片段自身差异的第 10 百分位（"这组身体实际能达到的最好一致度"）
    → 完全一致不可达（三个身体在 2D 投影下不可能重合）
- 分数 = 差异落在两锚点之间的位置
- **代价他们也写明了**：锚点来自片段本身，所以**分数只在本次视频内有意义，跨视频不可比**
- 落地检测（arrivals）：找肢体停止运动的时刻，要求速度真的"下陷"；不同人 130ms 内算同一次落地

**为什么对你价值极高**：这套"自校准 + 相对评分"正是**儿童体感观察**的核心方法 ——
儿童之间差距太大，绝对标准不可行；而"和老师示范的相似度"是很好的相对指标。
另外 `kids-motion-screening` 要的"连续观察"也正好落在"同一个人跟自己比"的语义上。

**但要接受它的代价**：跨视频不可比。所以"连续观察"要用**同一套锚点**（第一次建立，之后复用），
而不是每次重新测锚点 —— 这是他们没解决的问题（因为对方是一次性演示），你必须自己补。

## 三、已在你的项目里查实的三处

### ① `squat.hipDrop` 是死配置

`data/exercises.json` 第 97 行定义了 `hipDrop`，但：
- `primary` 是 `kneeAngle`，`fsm.signal` 是 `kneeAngle`
- 全文没有任何 guard / phase / flag 引用 `hipDrop`
- **只有 `squat.hipDrop` 用 `legLength`，所以 `legLength` 这条 scale 也是死的**

**判断**：目前无害（因为没被读），但如果以后要拿它做"髋下沉"告警，
会同时踩两个坑：分母随动作缩短（④）+ `space: "image"` 的 x/y 单位不一致（下一条）。
**建议：要么删掉，要么按 ④ 修好再用。**

### ② 4 个信号在 `image` 空间算欧氏距离 —— 换摄像头比例会漂

`resolveScale` 里的 `distance()` 直接用归一化坐标。而 MediaPipe 的 `landmarks`
**x 按帧宽归一化、y 按帧高归一化** —— 非正方形画面里两者不是同一单位。

vision-demos 在 `running/cadence-explained.md` 里明确记了这个坑：
> "a thigh and a shank are rigid segments whose length can't depend on which way the limb points
> （mixed units, **a tilted shank measured 45% longer than an upright one**; scaled, within 2%）"

**你涉及的位置类信号**（`space: "image"`）：

| 信号 | scale | 主轴是否一致 |
|---|---|---|
| `squat.hipDrop` | legLength | ❌ 分子纯竖向、分母含横向分量 |
| `jumping_jack.ankleSpread` | shoulderWidth | ✅ 都是横向为主，比值基本抵消 |
| `jumping_jack.wristHeight` | torsoLength | ✅ 都是竖向为主 |
| `high_knee.kneeHeightL/R` | torsoLength | ✅ 都是竖向为主 |

**实际风险（2026-10-28 处置）**：现在实测和上课都用 720p（16:9），偏差是恒定的、被调好的阈值吸收了。
**但**换 4:3 摄像头、页面被容器裁剪、或将来做手机竖屏 → 比例变了，调好的阈值就会漂，
而且**表现为"某个动作在某台机器上不准"，极难排查**（和你记过的"跨对象通用性"是同一类问题）。

**修法有两条，2026-10-28 选了「报出来」而不是「偷偷改」**：

- 技术修法（照抄 `gait.analyze`）：在距离计算入口按 `frameWidth/frameHeight` 缩放 x。
  但请注意代价：**这会同时平移所有已按 16:9 校准的阈值**（例：真实 45° 的躯干现在读 60.6°，
  修正后会读 45°，而 situp 的 68° / 45° 双阈值、wall_sit 的 ≤20° 全都得重调一遍）。
  在只支持 16:9 摄像头的阶段，这是"为了一个不存在的问题换掉所有已校准参数"，不划算。
- ✅ 实际做法：**运行期检测 + 明确告警**。`v1-counter.html` 的 `aspectWarning(w,h)` 在画面
  不是 16:9（容差 5%）时，在机位卡里显示「画面比例是 640×480（4:3），不是 16:9……
  计数可能偏多或偏少」，并写进设备清单与 README 的「已知约束」。
  一个**会被看见**的警告，比一个悄悄改变了所有阈值的修复更负责。

> 注：角度类信号（`jointAngle`）用 `space: "world"`（米制 3D），**不受这个影响**；
> 但 `torsoLean` 用的是图像坐标，**受影响** —— 这条区别值得记住。

### ③ 左右腿标签会互换

`running/cadence-explained.md`：
> "Left/right labels follow the model. **ViTPose can swap the legs for a cycle when they scissor in the image**"

**你的暴露面**：`high_knee` 是双通道各跑一个状态机（`kneeHeightL` / `kneeHeightR`）。
如果 MediaPipe 在双腿交叉时把左右关键点互换一个周期，会出现
"左腿计数跳到右腿" —— 总数不变（**所以自检全绿也不会发现**），但分腿统计错。

**建议（2026-10-28 已落地）**：`test-counter.mjs` 的高抬腿段现在除了总数，还断言**每个通道各自的计数**
—— 左右交替 10 轮 → `L=10 / R=10`；只抬左腿 → `L=10 / R=0`。
**总数对不代表分对**，这一条专治"总数不变所以自检全绿"。
标签互换本身程序分辨不出来（模型说换就换了），所以同时写进了 README 的「已知约束」，由老师肉眼纠。

## 四、值得借的工程实践（5 条，成本都很低）

**① `config.py` 每项都注释"为什么是这个值"**
不是"这是什么"，是"为什么是它"。例如：
```python
BASELINE_PERCENTILE = 10    # relative zero: the hanging plateau, not the minimum
REP_PEAK_FRACTION = 0.60    # rise past this share of rep height to confirm a rep
INFERENCE_HEIGHT = 1080     # ViTPose caps at a 2048px long edge
```
对照你的 `exercises.json`：`meta` 里已经有说明，但没有**逐参数**的"为什么"。
调参台（`tune.html`）的滑块 hint 是唯一载体，专家改配置时看不到。

**② 每个算法配一份 `*-explained.md`，末尾必须有「What this does not do」**
`dance_sync` 的局限清单写了 4 条（相对不是正确、片段相对、2D、不听音乐）。
这个习惯比写"功能列表"有用得多 —— 它挡住了销售过度承诺，也挡住了自己过度自信。

**③ 每次运行产出 `run.json`：配置 + 来源 + 成本**
你的项目有"参数存档"（下次进来还在），但没有"**这次运行的参数、时间、来源**"。
做验收报告、和老师对账时会需要。

**④ 两层 CSV：`summary`（一行一个 rep）+ `frames`（一行一帧）**
你的 CSV 是"一行一条成绩记录"。他们多一层 **per-frame 全量测量**，
好处是**事后可以离线重算**（相当于把 tune.html 的"缓存回放"能力导出了）。

**⑤ 模型回复缓存 + 分辨率解耦**
- `data/cache/` 缓存 gateway 回复 → **重渲染零成本**
- `EXPORT_HEIGHT` 只改输出视频高度，推理仍用 `INFERENCE_HEIGHT` → **调分辨率不产生新调用**
这条思路对你有用：你现在改渲染参数（骨架粗细、显示项）不影响判定，但**没有缓存判定结果**，
所以调参台每次都要重放。他们这套"判一次、渲染多次"的分离值得借鉴。

## 五、功能层面：你没有的四个动作

| 他们有的 | 你需要吗 | 备注 |
|---|---|---|
| **dance_sync**（多主体同步度） | ⭐ 值得 | 教学场景（学生 vs 老师示范）刚需，也是儿童体感的核心指标 |
| **running**（步频/步态） | 可考虑 | 体育课有跑步测试需求；但"跑"的判定比静止动作难（位移、机位） |
| **deadlift**（硬拉） | 可考虑 | 中学体育/健身房场景；用 SAM 分割杠铃片当"尺子"测高度，思路很妙 |
| **rock_climbing / _3d** | ❌ 不需要 | 攀岩细分场景，与体育课无关 |

**其中 `rock_climbing` 有一个思路倒是通用的**：它做的是"**同一路线的多次尝试对比**"
（`src/compare.py`，比较每次用了哪些点、顺序如何）。这正好对应你的
"**同一个学生跨多次课的对比**" —— 序列对比 + 顺序差异，比单看一个数字有信息量。

**另一个值得注意的技术**：`deadlift` 用 **Gemma VLM 逐帧判断"背部是直还是圆"**，
返回的是两个概率（`{"straight": 0.05, "rounded": 0.95}`），不是文字。

这是个很聪明的做法：**难量化的形态判断交给 VLM，不用自己训练模型。**
对你的意义：如果将来要做"动作姿态像不像标准示范"这类判断，
规则写不出来、又不值得训模型时，VLM 是个低成本出路。
**但它必须联网、按次计费，所以只能用在课后分析，不能用在实时** —— 和你现在的架构不冲突，是补充。

## 六、不建议借的

| 别借 | 原因 |
|---|---|
| ❌ **云 API + 按次计费** | 直接破坏「零依赖 / 完全离线 / 视频不出本机」的对外承诺 |
| ❌ **Gradio webapp** | 你是单文件 HTML 双击即开，教师端体验更好；Gradio 反而要装 Python 环境 |
| ❌ **时间戳输出目录** | 浏览器端没有目录概念，你的模型是"记录 + CSV 导出" |
| ❌ **用 ViTPose 替换 MediaPipe** | 精度更高但需联网、要上传视频、延迟到分钟级 —— 与实时课堂互斥 |
| ⚠️ **`side: "min"` 的取法** | 不是因为不好，而是**侧拍场景下应该按置信度选**（见二①）—— ✅ 已于 2026-10-28 落地 |

## 八、附：他们的数据流结构（供参考）

```
视频 → 逐帧姿态（云 API，可缓存）→ 信号 → 判定 → 渲染叠加 + 侧面板
                                    ↓
        <clip>_summary.csv（一行一 rep）   <clip>_frames.csv（一行一帧）
        reps.json  reads.json  summary.txt  run.json（配置/来源/成本）
        plots.png（曲线 + box plot）
```

**一个值得记的设计**：`webapp/` 通过 `subprocess` 从**外部**改写各 demo 的 `config.py`，
而**管道里没有任何一行代码引用 `webapp`** —— 删掉 `app.py`，每条管道照常运行。
这是很干净的单向依赖：**外围可以随便换，核心不知道外围存在。**
你的 `tune.html` 与 `tpc-*` 的关系已经是这个形状（共享存档，判定层不认识页面），继续保持。
